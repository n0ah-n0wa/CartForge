# Database

**Status:** conventions established. Flyway baseline `V1__schema_baseline.sql` is applied. Domain tables and entities are not implemented yet.

PostgreSQL is the authoritative persistence layer. Redis must not be treated as durable business state. See [ADR 0002](adr/0002-postgresql-source-of-truth.md) and [ADR 0003](adr/0003-redis-as-cache.md).

Shared Java types live in `com.example.ecommerce.common.persistence`. Future entities must follow these rules; they must not introduce a second persistence style.

## Engine and ownership

| Topic | Requirement |
|---|---|
| Engine | PostgreSQL |
| Migrations | Flyway; files are immutable once committed |
| Hibernate | `ddl-auto=validate` in every profile |
| Schema creation | Hibernate must not create or update tables |
| Java timestamps | `java.time.Instant` |
| Java money | `java.math.BigDecimal` |
| Database timestamps | `timestamptz` |
| Database money | `NUMERIC(19, 2)` |

## Persistence conventions

These conventions apply to every future table and entity.

### Primary keys

- Column: `id BIGINT GENERATED BY DEFAULT AS IDENTITY`
- Constraint name: `pk_<table>` (for example `pk_users`)
- Java: `Long` on `BaseEntity` with `@GeneratedValue(strategy = GenerationType.IDENTITY)`
- The database generates the value. Callers must not supply an `id` on create.
- Public business identifiers (for example `order_number`) are separate unique columns, not the primary key.

`User` is a reserved word in PostgreSQL. Table names are therefore always explicit and plural. Do not rely on Hibernate to derive table names from the class name.

### Timestamps

- Columns: `created_at timestamptz NOT NULL`, `updated_at timestamptz NOT NULL`
- Java: `Instant` on `BaseEntity`
- Hibernate sets `created_at` on insert (`@CreationTimestamp`) and `updated_at` on insert and update (`@UpdateTimestamp`)
- Persist UTC only. `hibernate.jdbc.time_zone` is `UTC`. Do not use `LocalDateTime`, `Date`, or server-local time for business timestamps.
- JSON at the API boundary uses ISO-8601 (`2026-08-22T18:30:00Z`).

### Naming

| Kind | Rule | Example |
|---|---|---|
| Table | plural `snake_case`, set with `@Table(name = "...")` | `users`, `cart_items` |
| Column | `snake_case`; Java `camelCase` | `stock_quantity` / `stockQuantity` |
| Primary key | `pk_<table>` | `pk_products` |
| Foreign key | `fk_<table>_<referenced_table>` | `fk_products_categories` |
| Unique constraint or unique index | `uq_<table>_<columns>` | `uq_products_sku` |
| Check constraint | `ck_<table>_<rule>` | `ck_products_price_non_negative` |
| Secondary index | `ix_<table>_<columns>` | `ix_products_category_id` |
| Foreign-key column | `<referenced_singular>_id` | `category_id`, `user_id` |

Hibernate physical naming is `CamelCaseToUnderscoresNamingStrategy`. That converts Java field names to columns. It does **not** pluralize table names. Every entity must declare `@Table(name = "...")` to match the Flyway table.

Use `PersistenceConventions` to build constraint and index names in migrations and later annotations.

### Foreign keys

- Every relationship column is a real PostgreSQL foreign key, not an unenforced `BIGINT`.
- Name the constraint `fk_<table>_<referenced_table>`.
- Name the column `<referenced_singular>_id`.
- JPA must use `@JoinColumn(name = "...")` that matches the migration.
- Default delete action: `ON DELETE RESTRICT` (same as `NO ACTION`). A parent row cannot disappear while children exist.
- `ON DELETE CASCADE` is allowed only for composition, where the child cannot exist alone (planned: `cart_items` when a cart is deleted). Associations such as `products.category_id` and `cart_items.product_id` stay `RESTRICT`.
- Category deletion must not cascade to products. The application rejects the delete or requires reassignment.
- Index foreign-key columns that are used as lookup or join paths.

### Unique constraints

- Enforce uniqueness in PostgreSQL, not only in Java.
- Name: `uq_<table>_<column>` or `uq_<table>_<col_a>_<col_b>` for composites.
- Case-insensitive uniqueness (user email) uses a unique index on `LOWER(email)`, named `uq_users_email_lower`. Do not rely on a case-sensitive unique constraint for email.
- Planned unique keys: email (case-insensitive), category name, category slug, product SKU, product slug, order number, `(cart_id, product_id)`, one cart per user (`user_id` on `carts`).

### Optimistic locking

- Versioned rows use `version BIGINT NOT NULL`.
- Java: `VersionedEntity` with `@Version Long`.
- Hibernate increments the version. A stale update becomes `OptimisticLockException` and must be mapped to HTTP 409.
- Required where the specification includes `version` or concurrent stock updates: **User**, **Product**, **Order**.
- Not required on Category, Cart, CartItem, or OrderItem unless a later requirement adds it.
- The `stock_quantity >= 0` check constraint remains the last guard if two transactions race.

See [ADR 0004](adr/0004-optimistic-locking.md).

### Decimal and money

- Never store money as `float`, `double`, `REAL`, or `DOUBLE PRECISION`.
- Amount columns: `NUMERIC(19, 2) NOT NULL` (`PersistenceConventions.MONEY_PRECISION` / `MONEY_SCALE`).
- Java amounts: `BigDecimal` with `@Column(precision = 19, scale = 2)`.
- Currency: `CHAR(3) NOT NULL` storing an ISO 4217 code. Java: `CurrencyCode`. Default: `EUR`.
- Price, total, unit price, and line total follow this pair of rules. Order items snapshot `unit_price` as `NUMERIC(19, 2)`.
- Monetary amounts that must not be negative also get a check constraint (`ck_<table>_<column>_non_negative`).

### Indexes

Add an index when a unique constraint does not already cover the column and the query path is real. Do not index every column.

Minimum indexes from the specification (unique constraints already cover several of these):

```text
users.email                 → uq_users_email_lower
products.sku                → uq_products_sku
products.slug               → uq_products_slug
products.category_id        → ix_products_category_id
products.active             → ix_products_active
products.price              → ix_products_price
products.name               → ix_products_name
categories.slug             → uq_categories_slug
orders.order_number         → uq_orders_order_number
orders.user_id              → ix_orders_user_id
orders.status               → ix_orders_status
cart_items.cart_id          → ix_cart_items_cart_id
cart_items.product_id       → ix_cart_items_product_id
```

Product text search uses PostgreSQL `ILIKE` / `LIKE`. A btree on `products.name` helps equality and sorting; a leading-wildcard search will not use that index efficiently. That limit is accepted at portfolio scale.

### Nullable and non-nullable

- Default: `NOT NULL`.
- `id`, timestamps, `version`, booleans (`enabled`, `active`), money amounts, currency, and required foreign keys are `NOT NULL`.
- `NULL` is allowed only when absence is meaningful. Planned optional text: category and product `description`.
- Boolean flags are `NOT NULL` with an explicit default (`enabled` / `active` default true where the specification says so).
- Application validation and database constraints must agree. The database is the last guard.

### Migration naming and versioning

Location: `src/main/resources/db/migration`.

Pattern: `V<major>__<snake_case_description>.sql`  
Example: `V2__create_users.sql`  
Regex: `V[1-9][0-9]*__[a-z0-9_]+\.sql`

Rules:

- Integer versions, no leading zeros, no gaps once a version is committed.
- One concern per file (one table family, or one additive change).
- Files are immutable after commit. Fix mistakes with a new version.
- Do not use repeatable (`R__`) migrations for schema.
- Do not use Hibernate to “repair” a missing migration.
- `V1__schema_baseline.sql` is infrastructure only (schema comment). It does not create domain tables.
- Domain tables start at `V2`. The specification’s example list used `V1` for users before the baseline existed. The applied sequence is:

```text
V1__schema_baseline.sql
V2__create_users.sql
V3__create_categories.sql
V4__create_products.sql
V5__create_carts.sql
V6__create_orders.sql
```

Later versions may add constraints, indexes, or supporting tables (for example checkout idempotency records).

## Planned domain model

Field lists are the specified columns, not an implemented schema. Apply the conventions above when these tables are written.

### User — `users` — `VersionedEntity`

`id`, `email`, `passwordHash`, `firstName`, `lastName`, `role`, `enabled`, `createdAt`, `updatedAt`, `version`

- Email is unique and compared case-insensitively (`uq_users_email_lower`).
- Password is stored only as a hash (BCrypt or Argon2).
- Role is an enum: `CUSTOMER`, `ADMIN`.
- Registration default role is `CUSTOMER`. Users are enabled by default.

### Category — `categories` — `BaseEntity`

`id`, `name`, `slug`, `description`, `active`, `createdAt`, `updatedAt`

- Name and slug are unique. Slug is URL-safe.
- Inactive categories are omitted from the default public catalog.
- Deleting a category must not silently delete products. Deletion is rejected when products exist, or requires explicit reassignment.
- When historical references exist, deactivation (`active = false`) is preferred over physical delete.

### Product — `products` — `VersionedEntity`

`id`, `sku`, `name`, `slug`, `description`, `price`, `currency`, `stockQuantity`, `categoryId`, `active`, `createdAt`, `updatedAt`, `version`

- SKU and slug are unique.
- Price is non-negative `NUMERIC(19, 2)` / `BigDecimal`. Currency is explicit; default is EUR.
- `stock_quantity` must never be negative (`ck_products_stock_quantity_non_negative`).
- A product belongs to a category (`fk_products_categories`, `ON DELETE RESTRICT`).
- Inactive products and zero-stock products are not purchasable.

### Cart and CartItem — `carts`, `cart_items` — `BaseEntity`

Cart: `id`, `userId`, `createdAt`, `updatedAt`

CartItem: `id`, `cartId`, `productId`, `quantity`, `createdAt`, `updatedAt`

- Each customer has at most one cart (`uq_carts_user_id`).
- Quantity must be greater than zero.
- The same product must not appear twice in one cart (`uq_cart_items_cart_id_product_id`).
- Cart contents do not reserve inventory. Stock is checked again at checkout.
- `cart_items` may use `ON DELETE CASCADE` from `carts`. `product_id` stays `RESTRICT`.

### Order and OrderItem — `orders`, `order_items` — Order is `VersionedEntity`

Order: `id`, `orderNumber`, `userId`, `status`, `totalAmount`, `currency`, `shippingAddress`, `createdAt`, `updatedAt`, `version`

OrderItem: `id`, `orderId`, `productId`, `productName`, `sku`, `unitPrice`, `quantity`, `lineTotal`

- `order_number` is unique and human-readable (example: `ORD-2026-000001`). It must not be only the internal id.
- Generation must remain unique with multiple replicas. The planned approach is a PostgreSQL sequence allocated inside the checkout transaction.
- Order items snapshot name, SKU, and unit price.

## Relationships and foreign keys

```text
User 1 ─── 1 Cart
Cart 1 ─── N CartItem
Product 1 ─── N CartItem

User 1 ─── N Order
Order 1 ─── N OrderItem
Product 1 ─── N OrderItem

Category 1 ─── N Product
```

## Constraints

Database constraints must complement application validation. At minimum:

| Invariant | Enforcement |
|---|---|
| Unique email | Unique index on `LOWER(email)` |
| Unique SKU, product slug, category name, category slug | Unique constraints |
| Unique order number | Unique constraint |
| Unique product per cart | Unique `(cart_id, product_id)` |
| One cart per user | Unique `carts.user_id` |
| `price >= 0` | Check constraint |
| `stock_quantity >= 0` | Check constraint |
| Line `quantity > 0` | Check constraint |
| Required columns | `NOT NULL` |
| Timestamps | `timestamptz` / `Instant` |

## Transactions

Services own transaction boundaries. Controllers must not begin or commit transactions.

Required transactional operations:

- checkout (all checkout steps in one transaction);
- order cancellation with stock restore;
- inventory modification;
- administrative order status updates where necessary.

Default PostgreSQL isolation is used unless a specific operation documents a stronger level. Transactions should stay as short as reasonably possible. Checkout must not perform remote I/O inside the transaction.

## Inventory storage

Inventory is `Product.stockQuantity`. Internal operations: increase, decrease, restore. There is no inventory table and no public inventory API.

## Idempotency records

Order creation should honor `Idempotency-Key` for the same authenticated user. Redis is allowed by the specification as a store, but Redis outage must not break the API. The planned store is a PostgreSQL table written in the same checkout transaction so duplicate submits cannot create two orders when Redis is down.

## Seed data

Development may load deterministic seed data: several categories, at least 15 products, at least one admin, and at least one customer. Credentials will be documented as development-only when that data is added. Production must not apply development seed users automatically.
